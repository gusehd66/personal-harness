# PM 항목 확장

## 요청 범위

추가 방법 분석과 실제 구현을 구분한다. 분석만 요청되면 변경 후보와 검증 계획을 보고하고 제품 코드·구조 문서를 수정하지 않는다. 추가 대상 product나 데이터 의미가 불명확해 설계가 달라지면 질문 후 답변 전까지 멈춘다.

## 구조 확인 후 설계

1. 현재 소스에서 대상 product의 입력 → 등록/선택 → 가공/집계 → 저장 → 조회 경로를 찾는다. 파일/장비 입력, 동기/queue 처리, 실제 저장소, 실행 classpath를 확인한다. 단계가 없거나 결합되어 있으면 현재 구조대로 기록한다.
2. 기존 category의 필드 확장인지, 새 category인지, 새 입력 형식/장비 지원인지 구분한다. 단위, counter/gauge, 수집 시각·구간, 식별 index, 결측·LOS, 저장·조회 호환성을 확정한다.
3. 같은 product의 유사 PM은 구현 참고로만 사용한다. 없으면 현재 product의 실제 소비자와 등록·가공·저장 계약에서 확장 지점을 찾는다. 다른 product 사례는 경로·등록·시간·식별자·저장소 차이를 비교한 뒤 적용 가능한 부분만 참고한다.
4. 기록된 Mongo 모델·static 등록·파일 parser 방식은 기존 프로젝트의 사례다. 다른 구조를 이 방식에 맞춰 재설계하지 않는다. 예를 들어 MariaDB mapper 기반이라면 DTO/가공 → service/mapper → table → 조회의 현재 계약을 확인한다. 새 저장 계층이나 공통 추상화를 추가하지 않는다.
5. 단계별 현재 근거와 변경 후보를 연결한다. 수정 파일, 호출자/등록/설정/테스트 영향, 기존 데이터 호환성, 검증 방법을 제시한다. 생성 파일은 생성 원본·도구를 먼저 확인한다. 원본을 찾지 못하면 임의로 생성 방식을 가정하지 않는다.

## 연결해야 할 책임

| 책임 | 추가 시 확인할 것 |
| --- | --- |
| 입력·등록 | 값이 실제로 들어오는가, 대상 NE/product로 선택되는가, 실행 코드가 로딩되는가 |
| 가공·집계 | 필드 변환·단위·시각·식별자, 평균/합계/차분, 행 결합과 구간 종료 |
| 저장 | 모델/DTO, collection/table·키·index, batch 분리, 부분 실패·재처리·중복 |
| 조회 | NE별 항목 목록, 필드·표시명·단위, filter/index, 기존 응답 계약 |
| 운영 연결 | 보존·정리·동기화가 새 데이터를 처리하는가, 다른 product에 영향이 있는가 |

이 표는 책임 확인 기준이지 필수 클래스나 파일 목록이 아니다. 기존 공통 경로로 해결되면 새 REST·worker·scheduler를 만들지 않는다. DB schema/index 변경이 필요하면 migration 계획과 검증을 포함하되 운영 실행은 별도 승인 범위를 따른다.

## 완료 기준과 기록

- 대표 비식별 입력 → 기대 가공 결과 → 저장 대상·필드 → 조회 항목을 연결해 검증한다. 기존 category 필드 추가는 과거 데이터에 필드가 없는 경우도 확인한다.
- 관련 실패 사례만 고른다: 미등록/미매칭, 결측·잘못된 입력, 시간 구간·식별자 분리, 부분 저장과 재처리. 저장 대역과 격리 파일 경로를 우선 사용한다.
- 구조가 기존 기록과 다르면 새 구조를 해당 프로젝트 문서에 기록한다. 기존 product 분류에 억지로 넣거나 사례를 공통 필수 규칙으로 승격하지 않는다. 분석만 요청됐으면 문서 갱신 후보로 보고한다.
- 실행하지 못한 검증은 분리한다. 모델 등록, DB 저장, 파일 성공 이동, 조회 노출을 서로의 성공 근거로 대신하지 않는다.
